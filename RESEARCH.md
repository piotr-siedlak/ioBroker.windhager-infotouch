# Research log and evidence matrix

Research date: 2026-10-22. This file separates **what a source states** from **what has been verified**. Nothing in
this repository has been tested against a real controller yet (see [DEVICE_SUPPORT.md](DEVICE_SUPPORT.md)).

Evidence levels used below:

| Level                    | Meaning                                                                                                                      |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| **manual**               | Stated in the vendor PDF. Says nothing about protocol paths.                                                                 |
| **community-tested**     | A community project's author reports using it against their own hardware. Not reproduced by us.                              |
| **community-documented** | Written down by a community project without a stated test.                                                                   |
| **fixture-tested**       | Exercised by this repo's tests against a _synthetic_ fake server shaped after the above. Proves our parsing, not the device. |
| **hypothesis**           | Plausible, not relied on.                                                                                                    |

## 4. Gas boilers, other fuels, heat pumps

- HeatNexus classifies gas/oil/condensing boilers, heat pumps, solar and cascades as **"integrated, unverified"**: they are described in its bundled database, "no hardware was available for testing". That is the verification level this project inherits.
- The manual is PuroWIN-only (M7).
- Therefore the adapter does **not** ship a gas-boiler-specific mapping. It exposes whatever the controller lists, with native names, units and ranges, under neutral ids. Semantic aliases (`boilers.boiler_1...`, `heatingCircuits.hc_1...`) from the project brief are deliberately **not** created, because the function-type ids (`fctType`) have no verified meaning for a gas appliance. Adding them is a profile layer to build once real gas-boiler captures exist.
- Only one `fctType` has observed context (14 on circuit-like functions in the HeatNexus sample) - recorded here as an observation, not used in code.

## 6. Open questions (need a real controller)

1. Exact paging contract for groups with more than 10 entries (P7).
2. `writeProt` type on the wire (boolean vs string): the parser accepts both.
3. Whether `lock: true` functions are readable by the end-user account (we skip them).
4. Whether a gas boiler behind InfoWIN Touch exposes the same lookup tree, and which `fctType` values it uses.
5. Request-rate tolerance of the controller: default intervals are conservative starting points, not measured.
6. Auth lock-out behaviour after repeated failures.
7. HTTPS availability: HeatNexus states there is no local HTTPS option; the adapter supports it only if a device offers it.
